# 库存联合排查与数据权限

同事直接聊天即可使用。无需新增 ERP 角色，也无需为了排查库存额外开通仓储页面。

## 同事可以怎么问

| 场景 | 示例 | 返回范围 |
|---|---|---|
| 库存使用追溯 | G10050LG01A-JH，亚马逊 2026-10-29 到 10-30 谁操作过库存？ | 授权渠道的 IO 执行人与关联调拨；说明执行人不一定是业务占用方 |
| 有货却无法确认订单 | 亚马逊这个 SKU 有库存，为什么确认订单提示不足？ | 当前渠道库存、锁定量、确认订单占用和预估预留；按实际代码分别解释口径 |
| 调拨 | 这个 SKU 昨天从亚马逊调到哪些渠道了？ | 本渠道参与、真实批次关联的调拨；不开放对方渠道所有库存 |
| 占用 | 哪些订单占着这个 SKU 的库存？ | 渠道共享占用数量；只有授权店铺站点内的订单明细可见 |
| 数据不一致 | 渠道库存与仓库库存对不上，查一下原因 | 本渠道关联物理批次的数量核对、仓储 IO 数量汇总；不返回成本或其他渠道逐项库存 |
| 在途 | 这个 SKU 的亚马逊在途被分给了谁，释放了吗？ | 本渠道参与的分配/释放数量、状态和去向渠道，不展开采购敏感信息 |
| 导出 | 把这个 SKU 在上述日期的渠道调拨证据导出 Excel | 同一授权范围、同一固定字段，最多 10,000 行；机器人发送附件 |

历史 IO/调拨查询一次最多 31 天；当前库存和当前占用是实时快照，不能据此还原某天库存。多渠道用户需要明确渠道；只有一个授权渠道时工具可以自动选择。当前占用不按“最近两天”过滤，以免漏掉更早产生但尚未释放的占用。

## 三种授权结果

- **允许**：页面权限明确，或命中已登记的业务能力且范围可核验。
- **权限不足**：已确认直接查询的目标页面无权，或明确超出授权渠道。
- **暂无法确认数据授权范围**：需求模糊、页面未匹配、缺少范围、角色/业务能力尚无映射。此时不执行范围不明的数据查询；请补充业务方向、渠道店铺或单据，不能声称用户无权或要求开通一个不存在的页面。

不允许用“排查”二字绕过权限。例如直接索要无权限的采购价、供应商资料、全仓调拨明细仍被拒绝。其他业务场景尚未登记跨模块数据能力时，可继续有权限的源码分析和页面查询，但不会自动开放任意表。

## 服务端边界

1. 每次工具调用重新解析飞书身份、有效 ERP 用户和角色。核心运营角色使用生产库既有 ID 映射，见 `src/guest/inventory-policy.ts`；不通过聊天自报身份或名称模糊匹配赋权。补充某个运营页面的角色不自动等于运营岗位。
2. `inventory_diagnose` / `inventory_export_file` 仅接受固定数据集、准确 SKU、渠道、可选国家/仓库/订单和日期。不接受模型编写的 SQL、字段、关联关系或权限条件。
3. `mc_role_data_scope.shop_group` 保留平台—店铺—站点的原始授权组合，0 表示该层级全部后代，负数按 ERP 规则视为无效选项。禁止将独立 IN 列表组合成不存在的授权。
4. 渠道库存是平台/国家共享资源，没有店铺归属。通过已授权店铺站点的国家推导可查看的共享数量。订单明细额外应用完整店铺站点条件。运营角色路径未配置店铺范围时不执行查询；已有品库存页面发起的关联诊断采用原生页面数据范围，不凭空要求PMC配置运营店铺。
5. 联合排查可以读取本渠道关联物理批次的共享数量汇总；不能据此读取其他店铺订单、其他渠道全量库存、采购价格、供应商、客户资料或自由文本备注。调拨中的订单号仅在订单本身有权限时返回。
6. 额外源码只开放已核对的库存调用链文件，项目目录、敏感路径、只读数据库及禁止执行 Shell 的限制保持生效。
7. 库存证据导出与查询使用同一编译器，每次重新授权；禁止改走任意表格生成工具借用另一页面权限。普通模块查询保留原页面权限入口。

## 数据口径与验证

- IO 通过 `virtual_batch_id = channel_stock_batch.id` 且商品、仓库、物理批次一致建立关系；无法建立可靠关联的旧记录不自动全库兜底。
- 调拨通过源或目标渠道批次关联，返回本渠道实际参与的记录；时间按创建时间筛选，同时返回执行时间。
- 当前占用同时区分 `OrderItemsShipDAO::getAuditedOrderItemsShip` 的确认口径与 `getEstimatedReserveQuantity` 的预估预留口径；两者可能重叠，禁止直接相加。ERP 的 Detail 方法与汇总方法状态条件不同，不能混用。
- 物理批次核对只返回总库存、所有渠道合计和当前授权渠道数量。仓储 IO 仅返回数量汇总，不能将同批次其他渠道的出入库归因于当前渠道。
- 数量限制和截断状态必须随结果解释；空结果不证明全公司不存在记录。没有历史快照时不能伪称已经恢复历史库存。
- 回归测试使用多渠道、多店铺、多国家、不同品类及历史日期边界的可执行数据库样本，覆盖跨范围泄露、伪造参数、角色撤销、固定导出与日期限制。

新增业务能力时需要核对真实数据关系并加入服务端模板与越权测试；不得只修改提示词以开放自由跨模块 SQL。


## 已有业务页面发起关联排查（2026-10-30）

新增 `inventory_case_open`：真实飞书消息包含库存原因/异常问题、精确品编码和国家时，可按现有页面1104（分渠道品库存）或1103（全渠道品库存）发起。页面元数据、本人实际权限均由服务端核验；1103保留ERP临时角色81/82只能看品类10的约束。不增加ERP角色，不要求仓储页面权限。

例如：“G10009-BKCH_04，加拿大，分渠道库存管理和全渠道库存管理页面的在库库存为什么不一致”。工具返回同品同国的两页数量组成、更新时间、直接VSKU/SKU关系，然后允许 `inventory_diagnose` 获取相关渠道批次、物理库存、IO、调拨、占用数量、在途分配。模型自报“诊断用途”不能赋权；直接索取无权模块的数据仍走原页面授权。

诊断范围绑定会话和ERP身份，每次调用重验来源页面，SKU关联在SQL中再次核验。新问题清除旧范围；“继续”“继续排查”等明确续问沿用原范围，writer冲突迁移时可转移；`/new`不继承。范围仅驻留内存，4小时过期；服务重启后需重新发送包含对象的业务问题。不允许自由SQL、任意字段或全表读取；订单明细仍查店铺权限，无店铺权限只返回占用汇总。证据导出复用相同限制。

当前新增页面路径只展开直接品→VSKU→SKU关系；复杂组合、同款替代和其他业务领域需要继续登记真实关联关系，不能简单求和冒充最大可售，也不能把缺映射解释成业务方无权。

本次验证：用ERP用户796实际权限成功读取该品加拿大证据。批次101404、仓库313的物理库存0，亚马逊渠道批次1741682库存55，覆盖页面80与25的差55。物理流水在2026-08-14入库55、2026-09-02出库55；同期受控关联渠道流水未命中。可以证实批次数量不一致，尚不能证明具体执行人或导致渠道未扣减的程序路径。没有修改、刷新或重算生产库存。


## 历史扣减订单追溯（2026-10-30）

“谁用了库存/这条扣减是哪笔订单”使用 `channel_io` → `channel_io_orders`，追问单条流水时传 `ioRecordId`。后者核对虚拟批次关系以及SKU、物理批次、仓库、推单秒级时间，包含已发货/已完成订单；不按当前占用状态或订单创建时间筛掉历史订单。订单明细仍校验平台—店铺—站点授权；同一授权查询也可生成证据导出。

- 平台订单号使用 `platform_order_id`，内部订单号为 `order_id`。
- `ship_create_time` 明确指发货明细创建时间，不是订单下单时间。
- ERP DATETIME 按北京时间解释，Unix推单时间使用显式UTC+8基准换算，不依赖数据库会话时区。
- `evidence_type=batch_and_push_second_match` 表示交叉匹配，并不是渠道流水存在订单外键。候选明细数量只覆盖本人可见范围；多候选、重复流水、数量不符或截断时不能任选一个订单认定对应关系。
- 无精确匹配时说明证据缺口，不得改用当前占用订单猜测；未命中物理IO也不能断言尚未发货，须结合发货状态和delivery_time。

实际只读验证：ERP用户655有权访问平台订单112-8095369-6984237（内部112-8095369-6984237-43）。渠道流水2230938在2026-10-29 19:31:44扣减1件；发货明细5491600的商品9916、物理批次104917、仓库281和推单时间均吻合，状态为已发货，出库发货时间23:15:07。旧回答中的111-8190873-2649803-142两条明细batch_id/push_datetime均为0，是当前占用，不能作为上述历史扣减的对应订单。旧工具只有当前占用路径，且原回复将发货明细创建时间误标成订单时间；本次新增历史路径并明确区分。
